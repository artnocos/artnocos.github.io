h2. どのように考えてきたか

どのように考えてきたかを書くにあたって、具体的な項目をもとに話をしていく

h3. １行の文字数と行数

コーディング規約には１行の文字数が規定されていることがある
多くの場合それは８０文字程度だったりする
* "Google C++ Style Guide - Line Length":https://google.github.io/styleguide/cppguide.html#Line_Length
* "Google C++ スタイルガイド - 行の長さ":https://ttsuki.github.io/styleguide/cppguide.ja.html#Line_Length

{% quote %}
Each line of text in your code should be at most 80 characters long.
コードの各行の長さは、最大80文字までとします。
{% endquote %}

"GNU":https://www.gnu.org/prep/standards/html_node/Formatting.html は最終カラムに行継続を示す記号を表示することを考慮して１文字少ない７９文字としている（芸が細かい）

{% quote %}
Please keep the length of source lines to 79 characters or less,
ソースコードの行長は79文字以下にしてください。
{% endquote %}

これらは昔、端末が横８０文字までしか表示できなかった頃の名残だ
印刷桁数が８０桁などのプリンタもあって、自分はＥＰＳＯＮのＲＰ－８０Ⅱ、ＶＰ－８００などを使っていた

「１つの関数は２５行以内にしましょう」という指針も見たことがある
端末に表示できる行数が２５行までだったりしたので

高解像度モニタが普及した今となっては桁数、行数を厳格に守る意味も減ってはきている

しかし、なぜそのような指針が生まれたのか？
それは画面に多くの情報を映し出して全体を把握しやすくするためだ

ウィンドウサイズを変えれば８０文字よりも多くの文字を簡単に表示できる今と違い、１行に８１文字あると折り返して次の行に１文字だけ表示されたりする
１文字表示するのに１行使ってしまうとその分、他の行を表示することができなくなる
１画面に表示できる情報量が減り全体を見渡すのが難しくなっていく

関数を２５行以内でという指針も２５行より多い行数だと一度に関数の全体を見渡せないので把握するのが難しいと考えられたからだ

プログラム構造を階層化して表現したり、関数などのプログラム要素を作り出してきたのは、細かい部分を割愛してなるべく多くの情報を一度に見渡して把握できるようにするためだ

そして様々なコーディング規約を見比べてみるとGNUなどのelseやwhileの後に @{@ を表示するためだけに独立して１行を占有するものは、１行を８１文字などにして１文字しか表示していない行を作っているのと同じ効果を生んでいる
それよりはGoogleのスタイルのようになるべく制御構造を少ない行数で表現して多くの情報を見られるようにするほうが好ましいと考える

h3. 今までに見たことがあるその他のスタイル

名前があるのかは知らないが、使われているのを見たことがある別のスタイルを取り上げてみる

h4. *elseを新しい行で始める*

{% highlight c %}
if (condition) {
    one();
}
else {
    theOther();
}
{% endhighlight %}

@else@ を新しい行ではじめて @if@ と桁をそろえることにより対応関係を分かりやすくするというものらしい
GNUのスタイルなども同様の考え方だ
しかしながらこれだと画面表示の最終行がifブロックの終わりの @}@ になっていると @else@ の処理があるかないか確認するために画面をスクロールさせたりしなければならない
ソースコードを読むとき画面だと目が疲れるので紙に印刷したものを読むことがあった、そのような場合もブロック終わりの @}@ でページが終わっていると、次のページを確認しないといけなくて面倒だった

K&RやGoogleのスタイルでは @if@ と同じ桁にある @}@ を探せば @if@ の処理がどこまで続くか分かるし、続けて同じ行に @else@ があれば対応する @else@ があるかないかもすぐに分かる

h4. *elseを必ず書く*

「 @if@ を書いたら必ず対応する @else@ を書く」というコーディング規約を見たこともある
それであれば @if@ に対応する @else@ の有無を確認する必要は無いと言える（必ずあることになっているので）
@if@ の条件で行う処理があれば、大抵の場合 @else@ に対応する処理があるものなので、処理の書き忘れを防止するために必ず書くようにするという趣旨らしい、言いたいことは分からなくもない
しかしながらそのような規約に従ってできあがったコードとして見たことがあるのが以下のようなものだ

{% highlight c %}
int func(int arg1, int arg2)
{
  if (arg1 < 0)
    {
      return FALSE;
    }
  else
    {
      /* do nothing */
    }

  if (arg2 < 0)
    {
      return FALSE;
    }
  else
    {
      /* do nothing */
    }

  ...

  return TRUE;
}
{% endhighlight %}

細かいところは覚えていないがGNUに似たスタイルを採用していたように思うのでそれにしてみた
@else@ を必ず書くと決められたルールに合わせて、中に書く処理がない場合は @/* do nothing */@ のようなコメントを入れるというルールも同時に採用されていた
これを見たときはあまりの見にくさに閉口した
@if@ の処理が１つあるだけなのに @else@ などで無駄に４行も増えている
続く関数本体の処理を見るには、ずっとスクロールさせていかないといけない
「 @else@ を必ず書く」とはしない方がいいと考える

上記のようなコードを書くとしたら私なら以下のようにする
（上記は古いコードの再現のために @int/TRUE/FALSE@ を使っているが、今書くならということで @bool@ で書き直している）

{% highlight c %}
bool func(int arg1, int arg2)
{
    if (arg1 < 0) return false;
    if (arg2 < 0) return false;

    ...

    return true;
}
{% endhighlight %}

@if@ で行う処理は別の行に書くことになっているスタイルが多いが、短く書けて見やすくなるなら（特に関数の最初にあるエラー処理など）１つの行に書くのもアリだと考える
先にも書いたが、規約だ、ルールだ、と決め始めると、表面的にルールに沿っているだけで元の趣旨とはあわないコードが量産されたりする
なので例外を認めることも重要だと考える
このあたりの「どういうときには規約に沿わなくてもいいか」を表現するのは難しく、例えば熟練の料理人なら自分で判断してその日の天候に合わせて作り方を調整できたりするが、アルバイト店員には「マニュアルに従って調理してください」と指導するしかない、というようなものかなと思う

h4. *関数名の後に空白*

世の中には「なんでそれにした？」のような私には全く理解不能なスタイルもあるが、決めた本人にはそれなりの理屈があるのだろう
時々見かけるスタイルでマジでやめてほしいと思っているのは関数名と @(@ の間に空白を入れるものだ
"GNUのコード例":https://www.gnu.org/prep/standards/html_node/CPU-Portability.html でも見かけた、これが元なのか？（ @write@ の部分）

{% highlight c %}
int c;
while ((c = getchar ()) != EOF)
  {
    unsigned char u = c;
    write (file_descriptor, &u, 1);
  }
{% endhighlight %}

私は括弧がついているかどうかで関数かどうかを判別しているので、関数名の後に空白があるとどれが関数呼び出しなのか一目で判別できなくて困るのだが、これを採用した人たちはこれが一番いいと思ったのだろう


h3. スタイルの一貫性

一貫したスタイルにするのが見やすいのは確かでIPAなど大抵のスタイルガイドではスタイルの一貫性を保てという
しかし意図的に一貫性を保たないようなスタイルを採用したこともある
世の中の大半のガイドに反して一貫性を捨てる決断をするのはかなり勇気が必要だった

それは昔作られたグローバル変数を山ほど使うような〇〇なコードを流用して後継機のソフトを作ることにしたプロジェクトでの話だ
できることなら全部一から書き直したい誘惑に駆られながら "Joel on Software":https://www.ohmsha.co.jp/book/9784274066306.html に書かれた "あなたが絶対すべきでないこと PART I":https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/ の戒めに従い流用することにした
流用するコードは採用するスタイルとあっておらずフォーマッターで一括変換することも考えたがJoel on Softwareの "氷山の秘密、明らかに":https://www.joelonsoftware.com/2002/02/13/the-iceberg-secret-revealed/ にあった『まだ出来てない部分のＵＩはまだ出来ていない *ように見える* ように作ることだ。』からの連想で、自分で確認していない部分、修正しない部分のスタイルは旧いままにしておき、新たに変えた部分だけ新しく決めたスタイルにする、という規約にした
ＵＩとは話が異なるが見た目だけきれいに整えてできた気になるのではなく、旧いスタイルになっている部分を見たら「ここは昔のままなんだな」と気付けるようにした

その昔アリスター・コーバーン氏の開発プロセスに関する講演を聞いたことがある
「開発プロセスはプロジェクト毎に異なるものだ、宇宙開発で使われるようなソフトウェアでは重厚なものになるし、それよりも小規模なプロジェクトではもっと軽量なものを採用しないと無駄に時間がかかってしまう」のような内容が印象に残っている
全てのプロジェクトに適用可能な唯一絶対の万能な開発プロセスというものはなく、開発プロセスというのはプロジェクト毎にテーラリングが必要という話だった

一貫したスタイルにするというようなほとんど自明のようなガイドでもプロジェクトによっては違う選択をすることもありうるということだ
プロジェクトで使用するコードに２つのスタイルが混在していると見にくいのは確かなので私とは違う選択をする人もいるだろう


h2. 所感

h3. スタイルなんてどうでもいいのか？

世の中には「スタイルなんてフォーマッターで揃えればいいじゃん」のような考えの人もいるようだ
事実、私が関わったプロジェクトの中でも「規約に合わせるためフォーマッターで揃えました」のようなことを言うメンバもいた

*違う 違う そうじゃ そうじゃない* んだよ

私は人のコードを読んだりレビューしたりすることが多いので見やすいスタイルにそろっている（フォーマッターでそろった状態に整形しておいてくれる）と見やすいのは確かだ
しかしそのコードを書いている本人はどうなのか
書いている最中は自分のコードを見ないのか
コードを書いている途中は適当に書いておいて最後に「決められているからそれに合わせておきました」というものなのか

コーディング規約を決める時、どのようにしておけばプログラムを書きやすいか、書いている途中で自分のコードを確認して間違いに気付きやすいか、を考えて決めている
書いている途中は何でもよくて最後に整形するというとまるで、原稿は手書きで書いておいてキレイに印刷するために最後にワープロに入力する、という昭和の話に聞こえる

ここまで私はこう考えているということを書いてきたが、スタイルはそれぞれの人がそれぞれの理由で決めているのだろう
だから私の考えたものに合わせろ！と言うものではない
私が期待するのは
*スタイルという見た目だけの話に思えるような細部においても、自分のプロジェクトにとって何がいいのか考えて！*
ということだ
決してGoogle様が決めたからそれに従いましょうとか、決められたからその通りにしますとか、ＡＩが出力したものをそのまま使いましたとか
そういうものではないと思う
空白がどこにあるか、どこに改行があるかのような、例えそれがプログラムの動作には影響がないようなものだったとしても

h3. ＡＩがコードを書くようになって

ソースコードのスタイルにこだわるのは人が読むためだ
プログラムの動作に関係がないとしたらスタイルはなんでもいいのか
ＡＩがコードを生成するのなら人の読み易さは関係ないのか
難読化されたJavascriptコードのようなものでもいいのか
自動翻訳があれば英語は勉強しなくていいのか
電卓があれば暗算はできなくていいのか

ＡＩの進化で世の中は便利になっている
一方 XAI (Explainable AI) という言葉もある、ＡＩの出力を解釈できないままなのはよくないという考えに基づくものだ
簡単な英語のあいさつも、簡単な計算も、自分ではできずに全てツールを通すのが本当にいいことなのか
人がコードを読むことを前提としないのなら、ＡＩが出してきたコードを見てもちんぷんかんぷんで、確認もＡＩにお任せ、ＡＩの書いたコードを解釈できなくてもいい、ということか
コードを自分の手で直接書かずＡＩの出力をコピペするだけ、コードは眺めるだけで読むこともしないとなると、どういうコードが読み易いかも分からなくなり、ひいてはコードを解釈する力も下がるように思う

h3. なぜコーディング規約を決めるのか

世の中でよく見る理由はだいたい以下のようなものだ
* 『書き方を統一すると、コードの読みやすさ、直しやすさが向上する』(Gemini)
* 『コーディング規約を決めると可読性と保守性が向上する』(Claude)

しかしこの説明には違和感があった
統一したり決めたりすれば読み易さや保守性が向上するのか？

*コーディング規約を決めると読みやすさが向上するのではありません
読みやすさが向上するようにコーディング規約を決めているのです* （ラクス構文）
